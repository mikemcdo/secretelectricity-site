TypeLock for Jira

Restrict who may create a specific work item type, by group or project role.

Jira grants Create Issues at the project level: anyone who can file a Bug can also create an Epic. TypeLock narrows that to a single work item type, so everyone can raise Bugs and Tasks while Epics stay with the people who own the roadmap.

The rule is enforced, not hidden. TypeLock adds a validator to the workflow's Create transition, which Jira evaluates server-side. The restriction holds whether the work item is created through the Jira interface, the REST API, or Jira Automation.

Setting up a rule

A rule lives on a workflow, so it applies to every project using that workflow. Set one up like this:

1. Open the workflow

Go to Project settings → Workflows for the project you want to restrict, and edit the workflow it uses.

You can also reach it from Settings → Issues → Workflows, but opening it from the project is better: the project-role picker only populates when Jira knows which project you mean. See restricting by project role below.

2. Select the Create transition

Switch to Text view, which lists transitions as rows, and select Create — the transition from Start to your first status. The diagram view works too, but the connector is a thin line and easy to miss.

3. Add the rule

Under Rules, choose View all, then Add rule. Pick TypeLock work item type restriction and choose Select.

4. Configure it

FieldWhat it does
Restricted work item type The one type this rule governs. Every other type is unaffected.
Allowed groups Members of any selected group may create it.
Allowed project roles Holders of any selected role may create it.
Error message Shown to anyone whose attempt is blocked. Say who to ask.

Groups and roles combine with or: a user is allowed if they are in any selected group or hold any selected role. A rule with neither is rejected when you save it, because it would block everyone.

5. Publish the workflow

Choose Update workflow. Nothing is enforced until you do — a draft has no effect.

Restricting by project role

The project-role list is populated only when the workflow is opened from a project's own settings. Opened from site administration, the picker is empty and says so.

The reason is that a workflow belongs to no single project — several may share it — so at site level there is no correct answer to "which project's roles?". Reading the list another way would require broad permissions over your user directory, which this app deliberately does not request.

Enforcement is unaffected either way. When someone creates a work item, Jira evaluates the rule against that project's roles.

What users see when blocked

Your configured message, in the create dialog. Through the REST API the request fails with HTTP 400 and the message in errorMessages. In Jira Automation the rule run is marked failed and the message appears in the automation audit log.

Things worth knowing

Administrators are not exempt

A rule restricting Epics restricts them for everyone outside the allowlist, including Jira administrators and the person who wrote the rule. This is deliberate — an exemption would be a hole in the control. Add yourself to an allowed group if you need to create the type.

Automation is not exempt either

A Jira Automation rule that creates a restricted work item type will fail unless the rule's actor is in an allowed group or role. If you have automation that creates Epics, set its actor to an allowed user, or add that account to an allowed group, before enabling a rule.

Renaming a group does not break a rule

Rules store group and role IDs, not names. Renaming a group leaves the rule working. Deleting one removes it from the rule, and if it was the only entry, the rule then blocks everyone — by design, rather than silently lapsing.

One rule per transition

Each rule restricts one work item type. To restrict two types, add two rules to the same Create transition.

Removing a rule

Open the Create transition, choose View all under Rules, use the ⋯ menu on the TypeLock rule and choose Delete rule, then Update workflow to publish. The restriction lifts immediately.

Privacy and permissions

TypeLock holds read-only permissions and cannot create, change or delete anything in your Jira site. It stores no personal data, runs no external service, and sends nothing outside Atlassian's infrastructure. Full detail is in the privacy policy.
